# D 阶段检索选型建议（RECOMMENDATION）

依据：[TECH_AUDIT.md](TECH_AUDIT.md)（实验前）与 [REPORT.md](REPORT.md)（实验后）。所有结论限定于本研究的合成数据集；数字引用自 `results/heldout.json`（保留集）。

## 1. 结论

**建议方案：Dense 为主的检索，FTS5 保留为事实一致的底座。** 具体是四件事：

1. **本地 Embedding + 对当前可信句柄的有效集合做精确向量扫描**，作为每轮自动上下文与 recall 的主排序。
2. **标识符精确命中置顶**：查询中带数字的拉丁词元（`ATL-2317`、`W1137`、`8443`）若被现有 FTS5 精确命中，这些记录排在最前。无参数。
3. **相似度下限**：低于下限的 Dense 候选不进上下文，把“库里没有相关记忆”时注入的条数从约 20 条降到 2–4 条。
4. **FTS5 原样保留**：它是事务一致的索引、Embedding 不可用时的完整降级路径、以及向量未建好的新记录的即时检索路径。

不建议采用最初预设的 D（FTS5 + Dense + RRF）与 E（再加查询扩展）作为最终形态：在本实验里它们没有超过单独 Dense，排序指标略低，E 还多一次模型调用。

**模型选择**（质量差距在统计噪声内，按成本与许可排序）：

| 候选 | 保留集 R@5 / nDCG@10 | 查询 p50（CPU） | 峰值 RSS | 模型文件 | 许可 | 评价 |
|---|---|---|---|---|---|---|
| **bge-m3 q8** | 0.950 / 0.918 | 25 ms | 1.3 GB | 570 MB | MIT | 许可最宽松，量化无损，延迟最低的大模型。**默认建议** |
| EmbeddingGemma-300m fp32 | 0.978 / 0.947 | 31 ms | 1.1 GB | 1.2 GB | Gemma 使用条款（非 OSI 许可） | 本实验实测最好，近似 ID 上也最强；采用前需确认其使用条款可接受。q8 版在 CPU 上更慢，不要用 |
| Qwen3-Embedding-0.6B fp32 | 0.962 / 0.929 | 163 ms | 4.0 GB | 2.4 GB | Apache-2.0 | 质量相当但内存与延迟是前两者的 4–6 倍；q8 版 R@1 掉 0.06；近似 ID 最弱。不建议 |
| multilingual-e5-small | 0.82 / 0.75 | 5 ms | 0.7 GB | 118 MB | MIT | 跨语言只有 0.50，不够 |

## 2. 对七个问题的回答

**1. 是否找到了比最初预设方案更好的方法？**
找到了一个更简单且不更差的组合：单独 Dense + 标识符置顶 + 相似度下限（报告中的 It 组）。相对预设的 D，它在保留集上 nDCG@10 持平或略高（0.942 对 0.919），近似 ID 压力集 R@5 1.00 对 0.80，无相关查询时返回 2.6 条对 20 条，并且少一个需要调的融合参数。审计阶段寄予期望的另一个候选——写入期文档扩展（F1）——**没有**胜出：+0.084 的 R@5，与查询期模型扩展同档，远低于 Dense。

**2. 当前 FTS5 真正需要解决哪些问题？**
- 词面缺口：同义、跨语言、需要推断的查询找不到候选（保留集 32 条失败中的 29 条）。这不是 FTS5 的缺陷，任何纯词面方法都一样，改切词/排序无效（实测 +0.00～+0.01）。
- 整句查询的规模问题：单字 OR 命中使候选集约为全库的四分之一，1 万条有效记录时 p50 0.54 秒、p95 2.1 秒，发生在每轮同步构建上下文的路径上。这个问题现在就存在，与是否引入向量无关。
- 没有相关性下限：库里没有相关记忆时仍注入约 15 条，而且 FTS 的分数区分不了有无答案（AUC 0.75）。
- 评测盲区：现有 14 条 recall 夹具全是关键词查询，而主路径是整句查询（基线 R@5：关键词 0.92，整句 0.58）。
- 64 词截断偏向单字：确实存在，修复不花成本，但本实验没有测到可见收益。

**3. 哪种方案实际收益最大？**
Dense embedding。保留集 R@5 从 0.633 到 0.95–0.98（配对 95% CI 下界 +0.22），跨语言类从 0.00 到 1.00。其余手段的收益量级：模型查询扩展 +0.11，写入期文档扩展 +0.08，词表 +0.02，FTS 修正 +0.01，在 Dense 之上叠加任何一种 ≈ 0。

**4. 哪种方案综合性价比最高？**
bge-m3 q8 或 EmbeddingGemma fp32 的 Dense 主排序 + 标识符置顶 + 相似度下限：每次查询约 30 ms 本机 CPU、无 API 费用、约 1.1–1.3 GB 常驻内存、每条记忆约 4.5 KB 派生存储，纯 npm 依赖。若 1 GB 级内存不可接受，次优且无新依赖的选择是模型查询扩展（B2），但它每轮多一次模型调用，收益只有 Dense 的三分之一。

**5. 哪些复杂技术不值得引入？**
- 向量数据库 / ANN / sqlite-vec：1 万条时精确扫描仍在 25 ms 内。
- 图检索 / GraphRAG：没有对应的失败类型；时间有效性已由 `correct` / `expires_at` / `claim_key` 处理，更正与过期类查询在所有方案下都是满分。
- Cross-Encoder 重排：无质量提升，长记录上变差，多 0.64 秒与 1.2 GB。
- RRF 混合与“混合 + 查询扩展”：不优于单独 Dense。
- 人工同义词表：开发集 +0.31，保留集 +0.02。
- 更大的 embedding 模型：600M 不优于 300M。
- 词典分词、trigram、jieba 扩展：收益 ≤0.012。

**6. 是否值得进入生产集成阶段？**
值得进入**带前置验证的、默认关闭的**集成，而不是直接上线。理由：收益大且稳定，安全不变量在实验里全部成立，降级路径等于现状。但有三件事本研究没有、也不被允许验证，必须先做：
- (a) onnxruntime-node 能否在目标 Host（Electron）进程内加载；不能则需要独立子进程或本机 HTTP 服务（如 Ollama）。
- (b) 用真实查询分布做影子评测。合成集里 40% 的可回答查询是改述类；§3.3 显示即使只有 20%，差距仍约 0.17，但真实数据可能有合成集没有的失败类型。
- (c) 相似度下限在真实记忆上重新标定。它与模型和量化方式绑定。
另外，无论是否做向量，§2 第二条的整句查询规模问题都值得单独处理。

**7. 若值得，怎样最小化修改现有 Memory 架构？**
见下一节。原则：SQLite Core 仍是唯一事实源；不改 Schema、不改写入路径、不改 ACL；新增的全部是可删除、可重建的旁路。

## 3. 最小集成方案

### 3.1 形态

```
可信句柄 ─► Core 有效集合（ACL / 状态 / 过期 / 证据 / 遗忘屏障）        ← 不变，权威
               │
   FTS5 ───────┤  现有 memory_fts，事务一致                               ← 不变
   向量 ───────┤  旁路文件 vectors.sqlite，条目绑定
               │  (memoryId, revision, contentHash, embeddingModelVersion) ← 新增，可删可重建
               ▼
   排序：标识符精确命中 → Dense（过下限）→ 预算（≤20 条 / 5000 字符）   ← 新增，可关闭
               ▼
   返回的行与正文一律取自 Core
```

参考实现：`src/lib/hybrid.mjs`、`src/lib/vector-index.mjs`（研究代码，不是可直接合并的补丁）。

### 3.2 对现有包的改动（按最小化排序）

1. **`character-memory-core`：一个只读扩展点，不改任何现有行为。**
   `recall(ctx, query, budget, options)` 增加可选的 `options.rank(rows, query)`：Core 照常用现有谓词取出有效行（需要把候选从“FTS 命中的有效行”放宽为“全部有效行”，仅当提供了 `rank` 时），交给回调返回排序后的 id，再由 Core 自己做去重、预算和冲突标注。未提供 `rank` 时逐字节走现有路径。相似度代码不进入 Core，Core 不依赖任何模型。
2. **新的可选插件（暂名 `character-memory-embedding`）**：持有 Embedding Provider 与旁路索引，向 Core 提供 `rank` 回调。默认不启用；不启用时系统与现在完全相同。
3. **索引维护**放在插件里，复用 Core 已有的空闲后台节奏（`drain` 的 5 秒轮询 + 空闲判断）：对当前句柄的有效集合计算“待建”集合（向量缺失或 `revision`/`contentHash` 不匹配）并补建。每条是独立的原子 upsert，可随时中断。
4. **遗忘 / 更正 / 过期不需要新的同步协议**：查询时以 Core 的有效集合与绑定为准，失配的向量不参与排序、不能返回任何内容（已测）。清理是卫生问题而不是安全问题，但向量是正文的有损副本，**遗忘后应尽快删除对应向量**——在同一后台循环里删除不再属于任何有效集合的条目，并在 `MEMORY-LAYERS.md` 的遗忘说明中写明“派生向量在下一次后台循环内删除”。
5. **不改**：Schema 3、`memories` / `memory_fts` / `experiences` 表、写入与提取路径、迁移脚本、Memory Tools 的工具签名、Inspector。

### 3.3 必须带上的行为

- **降级**：Provider 抛错、超时（建议 ≤300 ms）、返回非法向量、模型版本与索引不一致时，结果必须与当前 `recall` 完全相同。实验中逐条比对通过。
- **索引滞后补偿**：向量未建好的记录按其 FTS 名次参与排序，或在写入时同步建向量（单条 30–70 ms）。否则刚写入、刚更正的记录会被压到十名开外（实测第 16 位）。
- **先权限后相似度**：只扫描 Core 返回的有效集合；不做全库最近邻再过滤；不使用 ANN。
- **相似度不是事实或授权依据**：冲突标记、置信状态、`uncertain` 照常透出；下限只决定“放不放进上下文”，不决定真伪。
- **模型版本进绑定**：换模型 = 旧向量全部视为待建，期间自动走 FTS，无需停机迁移。
- **整句查询的 FTS 路径**：置顶规则只用带数字的拉丁词元去查 FTS，不再对整句做单字 OR；这同时消除了 §5.5 的规模问题在新路径上的影响。旧路径（未启用插件时）的规模问题需要单独立项。

### 3.4 上线前的验证顺序

1. Host 兼容性探针：在隔离 Home 的固定版本 Host 上加载 onnxruntime-node 并编码一条文本；失败则改用子进程方案。三个平台各跑一次。
2. 把本目录的一致性测试改写为针对真实扩展点的回归，加入 `tests/`。
3. 影子模式：插件只记录“新排序与现排序的差异统计”（不含正文），不改变实际注入的上下文；用它标定下限并确认真实查询上的收益。
4. 默认关闭发布；单实例开启；保留一键关闭（关闭后旁路文件可直接删除）。

### 3.5 平台与迁移

`@huggingface/transformers` + `onnxruntime-node` 提供 Windows / macOS / Linux 的 x64 与 arm64 预编译二进制，模型文件与平台无关，旁路索引是普通 SQLite 文件，可随数据目录迁移，也可以不迁移而在新机器上重建。Provider 接口只有 `embed(texts, kind)` 与 `modelVersion`，换成本机 HTTP 服务或远程 API 不影响其余部分；使用远程 API 会让查询与记忆正文离开本机，需要另行评估。

## 4. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 合成集高估收益 | 真实查询若多为关键词式，绝对收益变小 | 影子模式实测；§3.3 的敏感性表显示排序不变 |
| 原生模块无法在 Host 内加载 | 需要多一个进程 | 上线前第 1 步验证；Provider 可替换 |
| 约 1.1–1.3 GB 常驻内存与模型下载 | 低配机器不可用 | 默认关闭；按需加载；失败即降级 |
| 相似度下限误清空上下文 | 少数语义类查询拿不到任何记忆 | 保守标定（实验中 R@5 无损失）；标识符命中不受下限影响；主动 recall 工具仍可用 |
| 近似标识符 | Dense 混淆相近编号 | 置顶规则（压力集 1.00）；规则只覆盖“带数字的拉丁词元”，纯中文专名仍靠 Dense |
| 向量泄露正文信息 | 向量可被部分反演 | 旁路文件与 Memory 数据库同目录同权限；遗忘后删除；不上传 |
| 许可 | EmbeddingGemma 受 Gemma 条款约束 | 默认建议 MIT 的 bge-m3 |
| 本研究的未验证项 | 学习型稀疏未测；Dense 大模型之间的先后不可判定；质量只在约 470 条有效记录上测过 | 如需在模型间细选，应扩大保留集后再比 |

## 5. 如果不做向量

可接受的保守路线，按性价比：

1. 把整句查询的 FTS 词元改为“二元组 + 整词”，解决规模问题与无关注入（需要接受约 0.09 的 R@5 损失，或保留单字仅用于单字查询）。
2. 补充整句查询的 recall 回归夹具，让主路径有度量。
3. 修复 64 词截断顺序（零成本）。
4. 需要语义召回时，让模型在主动 `recall` 工具里换词重查——这是零依赖的查询改写，但不覆盖每轮自动上下文。

这条路线能解决现存的延迟与噪声问题，解决不了同义与跨语言召回。
