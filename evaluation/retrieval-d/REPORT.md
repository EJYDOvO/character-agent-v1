## 1. 摘要

1. **主要瓶颈是候选召回，而且是词面检索的固有限制。** 基线在保留集 83 条可回答查询中有 32 条在前 5 条里找不到目标，其中 29 条属于同义、跨语言或语义类；精确词、数字、ID、困难负例、生命周期、长文本类基线已接近满分。
2. **修 FTS5 自身（截断顺序、分词、词干）几乎没有收益**：R@5 +0.000～+0.012。
3. **词表扩展不泛化**：开发集 R@5 0.576→0.884，保留集只有 0.633→0.657（95% CI 含 0）。
4. **模型查询扩展与写入期文档扩展有中等收益**（保留集 R@5 +0.106 / +0.084），但跨语言类仍只有 0.17。
5. **Dense 的收益最大**：保留集 R@5 0.94–0.98，nDCG@10 0.92–0.95；跨语言 0.00→1.00。300M 参数的 EmbeddingGemma 不低于 600M 的 Qwen3-Embedding，multilingual-e5-small 明显不够。
6. **FTS5 + Dense + RRF 没有优于单独 Dense**，排序指标略降（nDCG@10 −0.01～−0.03）；在其上再加查询扩展（E）也没有可测收益。Cross-Encoder 重排同样没有带来提升，且每次查询多约 0.64 秒（CPU，20 对）。
7. **Dense 有两个具体弱点，都可以用便宜的办法补上**：
   - 近似重复标识符：ID 压力集上 Dense R@1 只有 0.10–0.50，FTS5 的 R@5 为 1.00。一条无参数规则（查询里带数字的拉丁词元若被 FTS 精确命中则置顶）把它补到 1.00，主集不受影响。
   - 无相关结果时照样返回 20 条：加相似度下限后，无关查询的返回条数 20.0→2.6（EmbeddingGemma），可回答查询的 R@5 不变。FTS5 的分数做不到这一点（AUC 0.75 对 0.96）。
8. **现有 FTS 路径有一个与质量无关的规模问题**：整句查询的延迟随库规模线性增长，1 万条有效记录时 p50 0.54 秒、p95 2.1 秒（§5.5）。
9. **安全与一致性**：所有组在两个划分、240 条查询上的越权/遗忘/过期返回均为 0；9 项一致性测试全部通过。测试中发现并处理了一个真实问题：索引滞后期间，朴素 RRF 会把刚写入或刚更正的记录从第 1 位压到第 16 位。

## 2. 实验设置

**数据。** 237 条手写记忆分布在四个可信作用域（主作用域 S0 187 条；另一主体 S1、另一 Character 命名空间 S2、另一项目 S3 共 50 条，其中多条与 S0 的事实同题不同值），含 9 条更正、8 条遗忘、6 条过期、2 组冲突、6 条 600–1500 字的长记录；另加 300 条确定性背景记录（仓储/设施日志领域，各带一个近似重复的记录编号）。全部通过未修改的 `LayeredMemory.remember / correct / forget` 写入。评测时 S0 的有效记录为 473 条。

**查询。** 开发集、保留集各 100 条，11 个类别；每个划分 83 条可回答、17 条“库内无相关记录”（含权限隔离与遗忘/过期类）。两种风格：`kw`（模型写给 recall 工具的短关键词，每划分 13 条可回答）与 `msg`（用户原始消息，对应每轮自动上下文，每划分 70 条可回答）。相关性 2 = 目标事实，1 = 仅话题相关；Recall/MRR/Precision 只计 2 级。

**ID 压力集。** 首轮开发集结果显示 Dense 在主集 `exact` 类上与 FTS5 持平，而主集里不同的标识符只有十来个，无法检验“Dense 不擅长精确标识符”这一常见论断。因此在评保留集之前增加 40 条查询（开发/保留各 20），在 300 个形如 `W1137` 的近似重复编号中查找指定的一条。它单独报告，不进入调参目标。

**公平性。** 所有组使用同一数据库、同一可信句柄、同一有效性闸门、同一候选预算（每路 top-50）和同一输出预算（≤20 条、渲染后 ≤5000 字符，与 `LayeredMemory.context()` 相同）。基线组 A 直接调用未修改的 `LayeredMemory.recall`；其余各组使用的 FTS 重表达与 A 逐查询比对，240/240 完全一致。

**调参。** 只在开发集上进行，目标为可回答查询的平均 nDCG@10：扩展合并方式（OR / RRF）、RRF 的 k∈{10,30,60} 与 Dense 权重 w∈{0.5,1,2,4,8}、凸组合对照的 α、相似度下限 τ（保持开发集 R@10 损失 ≤0.02 的最大值）。结果见 `results/tuning.json`。保留集在参数冻结并提交后评测一次。

**开发集首轮之后、保留集之前新增的对照组**及原因：

| 新增 | 原因 |
|---|---|
| RRF 权重网格从 w≤2 扩到 w≤8 | 首轮最优值落在网格边界 |
| G2：仅二元组/整词的 FTS 列表与 Dense 融合 | 首轮显示完整 FTS 列表（含单字命中）会拉低融合排序 |
| Ct / Ht / It：相似度下限 | 首轮显示所有组在“无相关结果”查询上都返回接近 20 条，而 Dense 的 top-1 余弦对有无答案有区分度 |
| I / It：标识符置顶 | ID 压力集显示按主集调出的 RRF 权重救不回精确标识符 |
| F3c：Dense + Cross-Encoder | 把重排器放在最好的候选列表上再测一次 |
| EmbeddingGemma q8 | fp32 版在开发集上表现突出，补测量化版 |

**模型。** Dense：Qwen3-Embedding-0.6B、bge-m3、EmbeddingGemma-300m、multilingual-e5-small，各测 fp32 与 q8，版本固定到 Hugging Face commit（`src/embed/models.mjs`）。重排：bge-reranker-v2-m3 q8。扩展：本机 Ollama `qwen2.5:7b`（Q4_K_M，digest `845dbda0ea48`），temperature 0、seed 7，输出缓存在 `dataset/expansions/`。

**未执行的预定项。** F4（bge-m3 学习型稀疏）没有运行：现成的 ONNX 导出只含 dense 输出，稀疏头需要另行从 `sparse_linear.pt` 提取并自行实现词权重计算与校验，本轮没有完成这项工作，因此**对学习型稀疏没有实验结论**。审计中的推断（非扩展式稀疏无法补上词面缺口）仍是未验证的假设。

开发集选出的下限在保留集上的效果（EmbeddingGemma q8，τ=0.264）：可回答查询平均返回 19.8→9.7 条，R@5、R@10 不变；无相关查询平均返回 20.0→2.6 条。代价：有 1 条语义类查询（h-sm-06）被下限清空（其目标本来也不在前 5）。下限是与模型绑定的经验值（Qwen3 0.405、bge-m3 q8 0.469），换模型或换量化必须重新标定。

### 3.6 失败案例

**基线 A**（保留集 32 条在前 5 未命中）：syn-zh 5、syn-en 6、xling 12（全部）、semantic 6、其他 3。典型：`爹妈那边多久联系一次`→“用户每周日上午给父母打视频电话”（爹妈/父母无共同字）；`Which days does he work from home?`→“用户每周二和周四在家办公”。

**B2 模型查询扩展**仍未命中 24 条，其中跨语言 10 条：7B 模型的扩展常是同语言近义词而没有给出译名，或译名与记忆用词不一致（如 `显示器`→`display` 而记忆写 `monitor`）。

**Dense**（EmbeddingGemma q8 + 下限，3 条未全中）：
- `h-sz-01 他平时怎么锻炼身体`：三条目标命中两条（健身房、徒步），羽毛球未进前 5。
- `h-sm-06 I need to send him a long status update, how should I format it?`→“回答先给结论、不超过三条理由”“工作回复不用 emoji”：需要推理，纯检索解决不了。
- `h-sm-07 他出差一周，家里有什么要照看的`：命中植物浇水，未命中“养了一只猫”。
这些都属于“需要由需求推断相关事实”的语义类，是所有方案共同的上限（最好成绩 0.85）。

**Dense 的系统性弱点**：ID 压力集。Qwen3-0.6B 对 `W1137` 返回的是一批编号相近的其他记录（R@1 0.10）。

**RRF 融合的退化**：FTS5 对整句查询的头部结果常是只共享功能字的无关记录，RRF 给它们与 Dense 头部同等的名次权重。开发集调参把 Dense 权重推到网格上限（k=10, w=8），等于让融合退化为 Dense；即便如此 nDCG@10 仍略低于单独 Dense。归一化凸组合对照与单独 Dense 持平，说明问题在“名次融合 + 噪声列表”，而不在混合这个想法本身——但两者都没有比单独 Dense 更好。

**Cross-Encoder**：把 long-noise 类从 1.00 拉到 0.86（长记录被 512 token 截断后目标句不在输入里），语义类 0.85→0.80。

**量化**：Qwen3-0.6B 的 q8 版 R@1 从 0.863 降到 0.803，bge-m3 与 EmbeddingGemma 的 q8 基本无损。

## 4. 一致性与安全验证（第四阶段）

`src/consistency.test.mjs`，真实模型（multilingual-e5-small q8），9/9 通过：

| 场景 | 验证内容 | 结果 |
|---|---|---|
| 跨主体 / 跨 Character / 跨项目 | 四个作用域的向量在同一个旁路文件里；用其他作用域记录的原文作查询（向量完全匹配） | 只返回本作用域记录；扫描数恰等于可信句柄的有效集合大小 |
| 未授权句柄 | 伪造句柄 | 在任何检索之前抛出 `Unauthorized` |
| 遗忘后向量未清除（索引器滞后/崩溃） | 用原文、关键词、英文改述查询 | 遗忘的 id 与正文都不返回；Core 的复活屏障仍拒绝重新写入同文；清除后向量删除 |
| 更正后向量仍是旧版 | 查询旧内容与新内容 | 旧绑定被识别为 stale、不参与排序；返回的只可能是新正文；新内容经事务一致的 FTS 立即可检索 |
| 过期记录带一条看似合法的向量 | 用原文查询 | 不返回；未来才到期的记录正常返回 |
| Embedding 抛错 / 超时 / NaN / 维度错误 / 模型版本变更 | 与 `LayeredMemory.recall` 逐条比对 | 结果完全等于 FTS5 基线，并标记 degraded |
| 新写入尚未建向量；索引器中途“崩溃”后重开 | 25/187 条已建 | 已完成的 upsert 完整保留、没有半写入；未建的由 FTS 提供；可续跑到 0 待办 |
| 冲突记录 | 同 claimKey 的两条 | 都返回并带 Core 的冲突标记；相似度不裁决真伪 |
| 写入期别名索引 | 更正、遗忘后用旧别名查询 | 旧修订的别名不匹配；遗忘记录的别名不可达 |

设计要点（`src/lib/vector-index.mjs`、`hybrid.mjs`）：

- 派生索引放在**旁路 SQLite 文件**，条目主键 `(memoryId, modelVersion)`，绑定 `revision` 与 `contentHash`（与 `memories.fingerprint` 同算法，实验中逐条断言相等）。
- **先权限后相似度**：先向 Core 取得可信句柄的有效集合，只对其中绑定匹配的向量做精确点积。不做“全库最近邻再过滤”。
- 返回的行与正文一律取自 Core，不取自派生索引。

**测试中发现的问题：索引滞后导致降权。** 刚更正的记录只出现在 FTS 一路，朴素 RRF 把它排到第 16 位（两路都出现的旧记录得分更高）。处理：对“向量待建”的记录，用它在 FTS 列表中的名次补上 Dense 一路的贡献，排名恢复到第 1。另一种办法是写入时同步计算向量（单条 30–70 ms）。无论采用哪种，这一点必须进入集成设计，否则“刚说的话反而搜不到”。

## 5. 性能与成本

### 5.1 Embedding 成本（CPU，onnxruntime-node，每模型独立进程）

| 模型 | 模型文件 | 加载 ms | 建索引 ms/条（批 8） | 单条更新 p50 ms | 查询 p50 / p95 ms | 峰值 RSS MB |
|---|---|---|---|---|---|---|
| multilingual-e5-small q8 | 118 MB | 1475 | 5.8 | 5.8 | 5.0 / 7.0 | 747 |
| multilingual-e5-small fp32 | 470 MB | 2013 | 7.4 | 8.1 | 6.9 / 8.7 | 1092 |
| EmbeddingGemma-300m fp32 | 1.2 GB | 3801 | 31.1 | 34.3 | 31.5 / 41.3 | 1068 |
| EmbeddingGemma-300m q8 | 309 MB | 1684 | 46.2 | 154.6 | 153.4 / 167.6 | 1642 |
| bge-m3 q8 | 570 MB | 2568 | 39.8 | 29.8 | 24.8 / 35.4 | 1320 |
| bge-m3 fp32 | 2.3 GB | 5467 | 73.2 | 66.6 | 59.8 / 81.3 | 1817 |
| Qwen3-Embedding-0.6B q8 | 614 MB | 2162 | 72.0 | 52.2 | 98.8 / 123.3 | 2946 |
| Qwen3-Embedding-0.6B fp32 | 2.4 GB | 8047 | 104.8 | 102.2 | 163.2 / 190.7 | 4021 |

- EmbeddingGemma 的 q8 版在这台 CPU 上单条推理反而比 fp32 慢约 5 倍（复测：q8 p50 172 ms，fp32 p50 29 ms），峰值内存也更高。原因未调查；结论是**该模型应使用 fp32**，两者检索质量无差别（§3.1）。
- 建索引：537 条记录全量编码 EmbeddingGemma fp32 约 17 秒、bge-m3 q8 约 22 秒、Qwen3 fp32 约 57 秒。1 万条按线性外推分别约 5、7、17 分钟，可在后台空闲时完成。
- 推理全部在本机，没有 API 费用。CPU 时间约为墙钟时间的 7 倍（onnxruntime 使用多线程），即一次查询 embedding 会短暂占满多个核。

### 5.2 查询路径延迟（不含模型推理；S0 有效记录 473 条）

| 步骤 | p50 ms | p95 ms |
|---|---|---|
| 生产 recall，关键词查询 | 0.97 | 9.5 |
| 生产 recall，整句消息查询 | 17.6 | 62.6 |
| 给定有效集合后的 FTS 排序 | 1.9 | 6.3 |
| 精确向量扫描，768 维 | 0.48 | 0.87 |
| 精确向量扫描，1024 维 | 0.59 | 0.76 |
| FTS + 扫描 + RRF + 预算 | 2.5 | 6.8 |
| 经 `browse()` 枚举有效集合（仅评测脚手架需要） | 15.3 | 21.6 |
| Cross-Encoder 重排 20 对（bge-reranker-v2-m3 q8） | 639 | 751 |

端到端估计（查询 embedding + 扫描 + 标识符 FTS）：EmbeddingGemma fp32 约 35 ms，bge-m3 q8 约 28 ms，Qwen3 fp32 约 165 ms。加 Cross-Encoder 再多约 0.64 秒，且再占约 1.2 GB 内存。

评测脚手架通过公开的 `browse()` 分页枚举有效集合（15 ms），生产集成应由 Core 内部一次 SQL 给出（`#rows` 已有同样的谓词），该项不计入方案成本。

### 5.3 模型扩展成本（本机 GPU，`qwen2.5:7b`）

| 用途 | 调用次数 | 平均输入 / 输出 token | 平均耗时 |
|---|---|---|---|
| 查询扩展（每次查询一次） | 200 | 164 / 30 | 553 ms |
| 文档扩展（每条记忆一次） | 538 | 196 / 69 | 1286 ms |

托管模型的费用 = 上述 token 数 × 供应商单价；本实验没有调用任何计费 API，不给出金额。查询扩展落在每轮自动上下文路径上，意味着每条用户消息多一次模型调用。

### 5.4 存储

派生向量索引（SQLite 旁路文件）：768 维约 4.2 KB/条，1024 维约 4.7 KB/条，384 维约 2.2 KB/条。1 万条 × 1024 维约 47 MB。评测用 Memory 数据库（537 条记录，含 WAL）5.9 MB。

### 5.5 规模

| S0 有效记录 | 生产 recall 关键词 p50 / p95 ms | 生产 recall 整句 p50 / p95 ms | FTS 物化候选数 关键词 / 整句 | 精确 768 维扫描 p50 / p95 ms |
|---|---|---|---|---|
| 473 | 0.97 / 9.5 | 17.6 / 62.6 | 17 / 132 | 0.48 / 0.87 |
| 2,173 | 1.0 / 51.9 | 91.7 / 378 | 62 / 563 | 2.4 / 7.0（投影） |
| 10,173 | 1.7 / 313 | 539 / 2119 | 268 / 2585 | 16.5 / 23.7（投影） |

- 精确扫描一栏在 2k 与 10k 规模用真实向量平铺到相应条数，只度量点积与排序的耗时，不含任何质量结论。1 万条时仍在 25 ms 以内，**不需要 ANN 或向量数据库**。
- **现有 FTS 路径在整句查询下随规模线性变慢**：整句中文查询通过单字 OR 命中约四分之一的库，全部物化并在 JS 中排序。1 万条时 p50 0.54 秒、p95 2.1 秒，而且这是每轮构建系统上下文时的同步调用。test.32 的“选择性物化”优化只对关键词查询成立。这是与召回质量无关、但同样需要处理的现存问题；只用二元组/整词作查询词元可把候选数降到原来的一小部分（§3.1 “A+ 仅二元组”：无相关结果时返回 1.8 条而不是 14.7 条），代价是召回下降约 0.09，因此它适合与 Dense 搭配而不适合单独使用。
- 进程峰值 RSS（性能脚本整体，含三个 q8 模型缓存向量与重排器）1671 MB。

## 6. 对实验前判断的核对

| 审计 §4 的判断 | 实验结果 |
|---|---|
| FTS5 的切词/排序修正解决不了主因 | 成立。R@5 +0.000～+0.012 |
| 词表扩展泛化存疑 | 成立。开发集 +0.308，保留集 +0.024 |
| 模型查询扩展未必比小模型 embedding 便宜 | 成立。本机 7B 模型 553 ms/次；EmbeddingGemma 31 ms/次且效果高得多 |
| 写入期扩展可能优于预设方案 | **不成立**。F1 +0.084，与查询期模型扩展相当，远低于 Dense。7B 模型生成的别名多是原词重排，很少给出译名；更强的模型可能更好，但本实验没有证据 |
| Dense 单独使用不如混合 | **不成立**。单独 Dense ≥ RRF 混合 |
| Dense 对数字/ID 不敏感 | 部分成立。主集的精确类不受影响；近似重复 ID 上确实失效，且模型间差异很大（Qwen3 0.10，EmbeddingGemma 0.50） |
| Hybrid 是召回最稳的 | 不成立（见上）；有效的是“Dense 为主 + 标识符精确命中置顶” |
| Reranker 提升排序但延迟不可接受 | 延迟不可接受成立；提升排序不成立 |
| 不需要向量数据库或 ANN | 成立（见 §5 规模表） |
| 学习型稀疏解决不了词面缺口 | 未验证（F4 未运行） |

## 8. 局限

- **合成数据、单一作者。** 语料、查询、标注出自同一作者；类别是按任务要求有意覆盖的，不代表真实分布（§3.3 给出敏感性）。绝对数值不可外推。
- **样本量。** 每类 2–12 条可回答查询，分类别数字的置信区间很宽；Dense 大模型之间的先后不可判定。
- **保留集是公开的复现夹具**，不是盲测；纪律靠提交顺序与哈希保证（README）。
- **扩展模型。** B2/F1 用本机 7B 量化模型，是 Host 模型效果的保守估计。
- **延迟。** 单机 CPU 数字；未测 GPU、未测 Electron 进程内加载。
- **规模。** 质量实验只在约 470 条有效记录上做；更大规模只测了延迟。
- **L3 排除、人格化用途 lane** 未纳入质量评测（与检索方案正交，隔离由 Core 既有测试覆盖）。
- **F4 学习型稀疏未运行。**
